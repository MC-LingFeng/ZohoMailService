# ZoHome 架构说明

## 项目结构

```text
ZohoMailService/
├── ZohoWeb/       React + Vite + Tailwind 网页
├── ZohoService/   NestJS API 与 Zoho Mail 接入
├── docs/          架构和开发说明
├── package.json   npm workspaces 与统一命令
└── .nvmrc         推荐 Node 版本
```

## 数据流

浏览器访问 Vite 的 `localhost:5173`，通过同源 `/api` 请求连接 NestJS。NestJS 负责工作区登录、Zoho OAuth、令牌续期、账号与邮件数据持久化，以及 Zoho API 请求。

### 按邮箱绑定应用配置

1. 用户在「添加邮箱」表单输入目标邮箱地址、Client ID 和 Client Secret，通过 `POST /api/auth/zoho/url` 提交给服务端。邮箱登录密码不在此表单中收集。
2. 服务端创建与当前工作区会话绑定的一次性 OAuth state，将待授权配置保存至数据库，其中 Client Secret 加密保存，待授权记录有效期为 10 分钟。
3. 用户在 Zoho 官方页面登录并同意权限；回调先校验 state 的会话归属、有效期和单次使用条件。
4. 服务端使用本次待授权记录中的应用凭据交换令牌，获取真实 Zoho 邮箱信息，并检查与表单目标邮箱是否匹配。不匹配时拒绝绑定并返回明确提示。
5. 成功后，在同一邮箱的账号记录上关联 Client ID、加密的 Client Secret 和加密的 Refresh Token。Access Token 仅在服务端内存中缓存并在有效期内复用。前端后续只通过内部账号 ID 调用邮件接口。

客户端仅在用户填写绑定表单时持有输入值，服务端不向账号列表或详情接口回传 Client Secret、Refresh Token，也不要求浏览器持久化这些凭据。环境中的工作区密码、令牌加密密钥和统一回调地址属于工作区配置；新绑定不依赖全局 `ZOHO_CLIENT_ID` / `ZOHO_CLIENT_SECRET`。全局应用凭据只作为旧账号记录的可选兼容回退。

### 重新授权与更换应用

对应账号的重新授权入口复用数据库里已保存的邮箱级应用配置，不要求用户再次填写 Client ID 或 Client Secret。刷新令牌时同样必须使用该邮箱关联的应用凭据。

「更换应用配置」会为同一个邮箱重新提交应用凭据并开启授权流程。原账号和原凭据在待授权期间保留，只有新授权成功且邮箱匹配后才替换。取消、超时或错误账号授权不会覆盖原连接。

演示数据和真实邮箱操作明确区分。演示发件仅写入本地示例数据；真实发件使用选定账号的授权，并由 Zoho 校验发件地址与账号权限。

## 页面分工

| 页面       | 目的                                                                    |
| ---------- | ----------------------------------------------------------------------- |
| 首页       | 介绍系统能力，展示当前数据与最近操作，进入工作台                        |
| 邮件工作台 | 切换账号，查看收件箱、垃圾邮件、已发送和邮件正文，撰写邮件              |
| 邮箱账号   | 搜索与分组邮箱、按邮箱填写应用凭据、重新授权、更换应用配置和断开连接    |
| 返利网     | 按邮箱记录返利网与 offer，管理收益、成本、结款、封户和 IP，对比汇总数据 |
| 使用指南   | 说明首次配置、添加邮箱、查看与发送邮件，以及授权和同步问题              |

### 返利网记录

`/rebates` 页面通过受工作区会话保护的 `/api/rebates` 接口读写当前模式的 SQLite 数据库，不请求外部返利网站。每条记录关联现有邮箱，保存站点、创建日期、offer、收益、成本、结款、封户和 IP 信息。金额按两位小数处理；页面中的「转化」先将成本和收益换算为整数分，再使用最大公约数约分为 `成本:收益`，例如 `20:400 → 1:20`。两者都为零时显示 `0:0`，仅成本为零时为 `0:1`，仅收益为零时为 `1:0`。原有数字 `conversionRate` 接口字段保留兼容，页面直接使用成本、收益计算比值。

列表分页与汇总独立：搜索、邮箱及状态筛选同时影响明细、总计和邮箱对比，翻页只改变明细。整体转化使用汇总成本和汇总收益约分。移除邮箱时同步清理其关联返利网记录。

总览及按邮箱对比只计入未封户记录的收益，但保留所有匹配记录的成本。收益进一步按结款状态拆分为 `settledRevenue` 和 `unsettledRevenue`，图表分别使用绿色与浅红色；同一邮箱可以同时出现两种分段。明细保留原始录入金额。转化除精确约分外，增加收益除以成本后保留三位小数的近似值：图表显示 `4:41 ≈ 1:10.250`，表格显示 `4:41 ≈ 10.250`；成本为零时近似值显示 `—`。

`GET /api/rebates/options` 从全部已有记录中读取去重、非空的返利网名称、域名与 Offer，沿用工作区会话和来源校验。表单打开时读取最新选项，与邮箱筛选和明细分页无关；输入新值并保存后可在后续表单中选择复用。

## 2000 账号的处理原则

账号列表可以分页显示，邮件按当前选中的账号加载。一次打开页面不应触发 2000 个账号的全量刷新。邮件列表与正文按需获取，列表与令牌可缓存；后台请求需排队、限制并发，并在限流时退避。对发信这种具有外部效果的请求不自动重试，以免出现重复发送。

按每个账号请求一次收件箱与垃圾邮件首页计算，2000 个账号每轮至少产生 4000 次列表请求。若每 5 分钟一轮，平均为 800 次/分钟，尚未包含分页、正文、发信与令牌续期。这是估算，不代表 Zoho 已为当前应用授予相应额度。

现阶段需要先完成少量免费账号的真实闭环验证，再确认单应用可连接账号规模、API 限流维度和持续运行表现。公开资料不足以承诺 2000 个免费账号实时同步。

## 数据与部署

SQLite 适合单实例本地首版。运行数据库和密钥不进入版本控制；备份数据库时须同时妥善保留对应的加密密钥。扩大到多实例部署时，应使用共享数据库与共享任务队列，统一维护会话、缓存和限流。

OAuth 回调 URL 必须与 Zoho API Console 中登记值一致。开发环境通过 Vite 代理接收回调，生产环境应使用自己的 HTTPS 域名，并由反向代理同时提供网页和 `/api`。

## 页面外观

所有页面使用统一 Tailwind 主题和公共样式类，提供 Light、Dark 和 Auto 三种外观。默认 Auto，显式选择保存到当前浏览器；Auto 会跟随系统外观变化。主题在 React 启动前应用，登录页、加载状态和服务离线页也能使用相同设置。
