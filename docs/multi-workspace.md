# 多账号与工作区

ZoHome 使用平台账号登录，再进入有权访问的工作区。每个工作区独立保存邮箱授权、邮件缓存、指纹浏览器、返利网记录和连接配置。平台账号和工作区成员关系统一保存在平台目录库中。

## 登录与首次管理员

真实部署使用 `APP_MODE=live`。第一次启动新版服务时创建初始平台管理员：

| 项目 | 初始值 |
| --- | --- |
| 用户名 | `admin` |
| 密码 | 当前服务端配置中的 `APP_PASSWORD` |
| 初始工作区 | `默认工作区` |

已有部署继续使用原 `APP_PASSWORD`，无需为升级重新生成密码或加密密钥。`APP_PASSWORD` 至少为 12 个字符，`TOKEN_ENCRYPTION_KEY` 为原有的 64 位十六进制密钥。

初始管理员只在平台目录库首次创建时初始化。以后修改 `.env` 中的 `APP_PASSWORD` 不会重置已保存的平台账号密码；该配置仍须保留有效值。登录后可在「系统设置」下方的「账号密码」中输入当前密码并设置至少 12 位的新密码。修改后，该账号在所有设备上的现有登录会话失效，需要重新登录。

演示模式保留自动进入演示管理员的体验，只用于演示数据。实际多人使用和真实邮箱部署应使用 `APP_MODE=live`。

## 创建账号和工作区

1. 平台管理员登录后进入「工作区管理」，在「创建平台账号」中填写用户名和初始密码。新账号不会自动加入已有工作区。
2. 已登录用户可以新建工作区，创建者成为所有者。新工作区从空白开始，不复制默认工作区的账号、返利网记录或演示样本。
3. 工作区所有者在「工作区成员」中按用户名添加已存在的平台账号，选择「成员」或「所有者」。
4. 用户通过顶部的工作区选择器切换当前工作区；工作区名称可由所有者在管理页面修改。

| 身份 | 权限 |
| --- | --- |
| 平台管理员 | 创建平台账号、维护平台设置，并访问和管理全部工作区 |
| 工作区所有者 | 使用本工作区业务功能，修改工作区名称、成员及工作区配置 |
| 工作区成员 | 使用已加入工作区的邮箱、浏览器和返利网功能，查看工作区配置 |

成员不是业务数据的只读角色；其不能修改工作区配置或管理成员。平台管理员在所有工作区拥有管理权限，不受普通成员角色限制。每个工作区至少保留一名所有者。

当前工作区选择保存在浏览器当前标签页的会话存储中。不同标签页可以分别打开不同工作区；账号登录 Cookie 仍由同一浏览器共享。切换工作区会重新读取当前空间的数据，编辑中的内容应先保存。

## 工作区设置与平台设置

「系统设置」默认显示当前工作区的配置，所有者可以修改。保存后对当前工作区后续操作生效，无需重启整个服务。

工作区配置包括：

| 字段 | 用途 |
| --- | --- |
| `ZOHO_MIN_REQUEST_INTERVAL_MS` | 当前工作区的 Zoho 请求间隔，至少 2100 毫秒 |
| `OUTLOOK_TENANT` | Microsoft 账号类型或租户，默认 `common` |
| `ZOHO_CLIENT_ID` / `ZOHO_CLIENT_SECRET` | 兼容旧授权；新邮箱仍可在绑定表单中填写应用配置 |
| `ADS_MANAGER_ACCOUNT` | 当前工作区的 Google Ads 经理号 |
| `ADS_API_VERSION` | Google Ads API 版本 |
| `ADS_CREDENTIALS_JSON` | 当前工作区的 Google Ads 服务账号 JSON |

Google Ads 的 JSON 由服务端加密保存在平台目录库中，页面只返回是否已配置；留空保留原值。新工作区不能通过填写服务器文件路径读取其他工作区的凭证。默认工作区升级时会导入原有 Ads 设置；存在旧凭证文件时，其内容会一并导入，原文件保留。

平台管理员还能切换到「平台设置」，维护服务端 `.env` 中可编辑的监听、页面与 OAuth 回调地址、运行模式等配置，保存后仍需重启服务。平台页的 `APP_PASSWORD` 仅作首次管理员初始化用途，旧版工作区连接字段也为只读；账号密码通过下方「账号密码」表单修改，Zoho、Outlook 和 Ads 的工作区字段通过「工作区设置」修改。已有有效平台加密密钥同样只读并保持原值。工作区成员不会读取平台设置接口。

`TOKEN_ENCRYPTION_KEY` 保护平台目录库中保存的工作区密钥与设置。已有目录库必须继续使用对应的原密钥；修改登录密码不需要修改该加密密钥。

## 旧版数据自动迁移

第一次使用新版启动当前模式时，服务会将原单工作区数据库接入「默认工作区」。升级前先停止旧服务，备份整个 `DATA_DIR` 和对应的服务端配置文件，再启动新版。不要让旧服务与新版服务同时使用同一数据目录。

迁移过程会：

1. 检查原 `live.sqlite` 或 `demo.sqlite` 的完整性。
2. 使用 SQLite 一致性快照生成备份，包含已提交到 WAL 的数据。
3. 将快照放入新默认工作区目录，校验副本的 SHA-256，并记录各表行数。
4. 建立平台管理员、工作区及其关联，继续使用原有业务数据的加密密钥。

邮箱、浏览器、返利网记录的 ID 与既有关系继续保留，已有邮箱授权无需重新绑定。原模式数据库及其 WAL 文件不会被迁移流程删除或覆盖。每种运行模式分别初始化平台目录库并迁移该模式的数据；切换模式不会把演示数据写入真实空间。

迁移后的目录示例：

```text
DATA_DIR/
├── platform-live.sqlite
├── workspaces/
│   ├── <默认工作区 UUID>/
│   │   └── live.sqlite
│   └── <新工作区 UUID>/
│       └── live.sqlite
├── backups/
│   ├── single-workspace-live-<默认工作区 UUID>.sqlite
│   └── single-workspace-live-<默认工作区 UUID>.json
└── live.sqlite                  # 保留的旧版原数据库
```

SQLite 运行时还可能生成 `-wal` 和 `-shm` 文件。JSON 迁移清单保存快照校验值、表行数、时间和路径，便于检查备份。若平台密钥不匹配，或任何已初始化工作区的数据库缺失，服务会报错，不会以空数据库代替原数据。

无需手工将单个旧 `.sqlite` 文件移动到新工作区目录。已经完成迁移后，替换顶层旧 `live.sqlite` 也不会覆盖正在使用的默认工作区。

## 备份、恢复与迁移机器

平台目录库保存用户、成员关系以及加密后的工作区密钥和配置；`workspaces/` 保存各工作区的业务数据库。它们共同组成一套数据。

备份或迁移时先停止应用，然后一起保存：

- 整个 `DATA_DIR`，包括 `platform-*.sqlite`、`workspaces/`、迁移备份和仍存在的 SQLite 辅助文件。
- 与该目录库对应的原 `TOKEN_ENCRYPTION_KEY` 所在配置文件，例如 `ZohoService/.env` 或桌面版 `zohome.env`。
- 演示模式未配置有效密钥时生成的 `DATA_DIR/platform-demo.key`；该文件已包含在整个目录备份中。
- 仍使用的旧版外部 Google Ads 凭证文件（如有）。

不要只复制运行中的主 `.sqlite` 文件，或只移动某一个工作区目录。恢复时使用同一套备份的目录库、工作区数据库和原平台密钥，避免成员关系或解密密钥不配套。

新版会按当前 `DATA_DIR` 重新推导工作区数据路径，支持将整套数据目录搬到其他机器或 EXE 目录。迁移机器后还需按实际访问地址维护页面、OAuth 回调及外部凭证配置。

## Docker 部署

Docker 沿用现有的两个挂载：应用配置文件和整个 `/app/data`。无需为每个工作区单独增加卷。

```sh
docker compose down
# 停止后，在受保护的位置备份原应用配置和完整数据目录。
docker compose up -d --build
```

继续使用原 `ZOHOME_ENV_FILE`、`ZOHOME_DATA_DIR` 及文件权限配置。首次更新启动会在同一数据卷内创建平台目录库、迁移备份和工作区子目录，原授权所用的 `TOKEN_ENCRYPTION_KEY` 必须保留。不要通过切换到新的空卷代替升级原数据。

首次部署空目录时，用 `APP_MODE=live`、有效的 `APP_PASSWORD` 和 `TOKEN_ENCRYPTION_KEY` 初始化；管理员使用 `admin` 与该初始密码登录，然后创建账号和工作区。应用配置仍不进入镜像。挂载、端口与权限步骤见 [Docker 使用与持久化](docker.md)。

## API 与隔离边界

浏览器业务请求通过 `X-Workspace-Id` 指定工作区，服务端同时校验登录用户对该工作区的权限。知道其他工作区的 UUID 不会获得其数据权限。未携带该头的兼容请求使用默认工作区，但仍须通过权限检查；新调用方应始终明确指定工作区。

| 接口 | 用途 |
| --- | --- |
| `POST /api/session` | 使用 `{ username, password }` 登录 |
| `GET /api/me` | 当前用户及其可访问的工作区 |
| `PATCH /api/me/password` | 使用 `{ currentPassword, password }` 修改当前账号密码 |
| `GET/POST /api/workspaces` | 列出可访问的工作区或创建新工作区 |
| `PATCH /api/workspaces/:id` | 修改工作区名称 |
| `GET/POST /api/workspaces/:id/members` | 读取或添加工作区成员 |
| `PATCH/DELETE /api/workspaces/:id/members/:userId` | 修改成员角色或移除成员 |
| `GET/POST /api/users` | 平台管理员列出或创建账号 |
| `GET/PATCH /api/workspace-settings` | 当前工作区的配置 |
| `GET/PATCH /api/settings` | 平台管理员维护服务端环境配置 |

业务接口继续使用 `/api/accounts`、`/api/rebates`、`/api/fingerprint-browsers` 等路径。每个工作区使用独立 SQLite 数据库、业务实例、邮箱缓存和令牌续期状态；Excel 全量替换、邮箱移除和 Ads 成本刷新只操作当前请求所属工作区。

前端切换时会取消旧工作区请求并重建页面状态。已经送达服务端的操作仍绑定发起时的工作区，不会随界面切换写入其他空间。

Zoho 和 Outlook 授权状态绑定发起授权时的用户、会话、工作区及服务商。回调会再次校验授权状态和工作区权限，并将浏览器带回发起授权的工作区；授权过程中切换其他标签页的工作区不会改变保存位置。

测试应使用独立临时数据目录。升级程序及测试不会替用户清理原数据库、迁移备份或外部凭证文件。
